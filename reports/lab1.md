# Ch3实验报告

## 功能设计&实现

- 为了实现request 0/1，需要实现内存地址读写，在unsafe代码块中进行类型强制转换即可（和C/C++类似，参考`ch3_trace.rs`代码也可以完成。
- request 2实现稍微复杂一些，需要统计当前task的syscall次数，由于数据和task相关，因此考虑保存到TaskContext当中。这里使用最简单的数组存储对应调用次数（没有std库，无法简单使用哈希表），考虑到系统调用号是有上限的，这点空间开销可以接受，并且这样可以降低更新统计信息的时间开销（相比逐个对比syscall类型）。需要注意的是根据题目要求，需要在syscall进行之前就更新统计数据。此外`TASK_MANAGER`的`inner`的锁不支持嵌套，多次获取对象会导致死锁。

## 简答

1. （sbi版本： rustsbi-qemu Prereleased 2024-03-24）  
   
   - 访问非法地址（`ch2b_bad_address.rs`）：PageFault in application, kernel killed it.  
     内核检查到非法行为后杀死了对应的task。
   
   - 使用S态指令（`ch2b_bad_instruction.rs`）：
     IllegalInstruction in application, kernel killed it.  
     内核同样杀死了对应的task。
   
   - 访问S态寄存器（`ch2b_bad_register.rs`）：
     IllegalInstruction in application, kernel killed it.  
     内核同样杀死了对应的task。  
     可以观察到程序后面的`panic!("FAIL: T.T\n");`没有正常执行，说明task确实被杀死了。对应的内核输出是由`trap_handler`产生的，这里kill task的实现也比较简单，直接执行`run_next_app`。  

2. 问题  
   
   1. 刚进入`__restore`时，`sp`代表的是内核栈指针位置。`__restore`函数的两种使用场景：
      
      - 应用开始执行
      - 从陷入态返回用户态
   
   2. 这几个寄存器和CPU执行密切相关
      
      - sstatus记录了处理器在S态的状态，其中SPP位为0时表示陷进来自U态，sret后会返回U态，SIE位为全局中断使能位，陷进发生时会被清零，sret之后恢复原值
      
      - spec记录了触发陷阱的指令地址，返回U态时回到原地址继续执行，如果需要从下一条指令开始执行还需要手动自增
      
      - sscratch用于临时存储上下文，在U态保存内核栈地址，S态为0，返回U态之前需要恢复为内核栈。
   
   3. x2和x4分别是sp和tp，保存栈指针和线程指针，sp由L60 `csrrw`切换，tp不是多线程环境，没有作用
   
   4. 执行指令之后，sp指向用户栈，sscratch指向内核栈
   
   5. 状态切换发生在sret指令，前面已经将sstatus的SPP位设置为0，CPU会根据这一位的状态切换到U态
   
   6. 这行指令交换了`sp`与`sstatus`寄存器，交换之后`sp`指向内核栈，而`sstatus`指向用户栈
   
   7. 从U态切换到S态通过`ecall`指令触发，触发异常导致CPU从U态切换到S态并进行相应的处理
